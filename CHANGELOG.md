# История изменений

## Доработка: справочники, чат, удаление записей и надёжность

Крупная доработка исходной версии. Ниже — что изменилось и почему.

### Справочники вместо перечислений в коде

Значения, которые раньше были захардкожены (`pgEnum` в схеме и словари подписей в
`src/lib/labels.ts`), вынесены в таблицы и редактируются в новом разделе
**«Справочники»** (`/directories`, право `directories.manage`):

| Справочник | Таблица | Заменил |
|---|---|---|
| Типы работ | `ticket_types` | enum `ticket_type` |
| Приоритеты и SLA | `ticket_priorities` | enum `ticket_priority` |
| Категории оборудования | `catalog_categories` | enum `catalog_category` |
| Единицы измерения | `measure_units` | свободный текст в `catalog_items.unit` |
| Роли и права | `roles` | enum `user_role` + матрица в `rbac.ts` |

Каждый справочник — отдельная страница: категорию оборудования заводят в справочнике,
а не на экране создания номенклатуры. Записи со `is_system = true` переименовываются и
отключаются, но не удаляются. У приоритета появилось поле `sla_hours`: если срок заявки не
задан вручную, он вычисляется как «сейчас + SLA приоритета».

Перечислениями остались только значения, с которыми связана логика кода: `ticket_status`
(автомат переходов), `unit_status`, `location_type`, `stock_tx_type`, `reservation_status`.

### Роли с настраиваемыми правами

Жёсткая матрица `Record<UserRole, Permission[]>` заменена ролями в БД. Роль — это набор прав
(отмечаются галочками, сгруппированы в `PERMISSION_GROUPS`), область видимости данных
(`scope`: `all` / `team` / `client`) и признак полевого персонала (`is_field_staff`).

Права роли загружаются в сессию при входе (`SessionUser.permissions`), а проверки везде
переведены с кода роли на право или на `scope`:

```diff
- if (can(user.role, "tickets.assign")) …
- if (user.role === "technician") …
+ if (can(user, "tickets.assign")) …
+ if (user.scope === "team") …
```

Защиты от самоблокировки: нельзя удалить роль, назначенную сотрудникам, снять право
`users.manage` с последней роли, где оно есть, или удалить последнего администратора.

Новые права: `directories.manage`, `tickets.delete`, `chat.write`, `chat.internal`.

### Чат по заявке

Таблица `ticket_comments` развёрнута в ленту обсуждения (`is_internal`, `author_name`,
`edited_at`, индекс по `(ticket_id, created_at)`), добавлены сервис `src/lib/services/chat.ts`,
эндпоинты `/api/v1/tickets/{id}/chat` и компонент `TicketChat`.

* Внутренние сообщения видны только сотрудникам с правом `chat.internal`; заказчик получает
  лишь открытые, а его собственные сообщения сервер всегда публикует как открытые.
* Новые сообщения подтягиваются опросом (`?afterId=`) раз в 7 секунд и при возврате на вкладку —
  без веб-сокетов, чтобы развёртывание оставалось «docker compose up».
* Автор удаляет свои сообщения, администратор — любые. Имя автора хранится в сообщении, поэтому
  переписка читается и после удаления сотрудника. В завершённой заявке лента только для чтения.

Старый эндпоинт `POST /api/v1/tickets/{id}/comments` заменён чатом.

### Удаление записей с проверкой зависимостей

Новый сервис `src/lib/services/deletion.ts` и `DELETE`-эндпоинты для клиентов, объектов,
сотрудников, бригад, автомобилей, номенклатуры, серийных единиц, заявок и записей справочников.

Ошибку ввода можно исправить, историю — нет: перед удалением считаются ссылающиеся документы,
и при их наличии возвращается `409` с перечнем помех и предложением деактивировать запись.

```json
{ "ok": false, "error": { "code": "CONFLICT",
  "message": "Нельзя удалить — на запись ссылаются: заявки: 3, объекты: 1, складские операции: 1. …" } }
```

Полная таблица правил — в [docs/09-directories-chat-deletion.md](docs/09-directories-chat-deletion.md).

### Валидация запросов

Ручной разбор тела (`num()`, `str()`) заменён zod-схемами в `src/lib/validators.ts`;
роуты используют `parseBody(req, schema)`, `parseQuery(req, schema)`, `parseId(params)`.
Ошибка приходит с указанием поля: `400 BAD_REQUEST`, `"name: не может быть пустым"`.

### Конкурентный доступ

* `changeStatus()` — заявка читается `SELECT … FOR UPDATE` внутри транзакции, поэтому допустимость
  перехода проверяется по актуальному статусу: два одновременных перехода больше не расходятся
  с историей статусов.
* `adjustBalance()` — строка остатка сначала создаётся (`INSERT … ON CONFLICT DO NOTHING`), затем
  блокируется `FOR UPDATE`: параллельные выдачи одной позиции не могут увести остаток в минус.
* `getUnit()` блокирует серийную единицу на время складской операции.

### Отчёты

Добавлены SLA-метрики: среднее время реакции (до взятия в работу), время решения, полный цикл и
доля заявок, выполненных в срок. Разрезы по типам и приоритетам строятся по справочникам.
Полевой персонал в отчёте о загрузке определяется признаком роли, а не кодом `technician`.

### Развёртывание

`docker-compose.yml` больше не подставляет небезопасные значения по умолчанию: без
`POSTGRES_PASSWORD` и `AUTH_SECRET` запуск останавливается с понятным сообщением.
