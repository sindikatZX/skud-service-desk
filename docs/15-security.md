# 15. Безопасность

Документ описывает, как система защищает данные, и что было исправлено при разборе.
Модель угроз простая и реалистичная для внутренней системы: сотрудник с лишним
любопытством, подобранный пароль, чужая вкладка в браузере сотрудника, клиент в портале,
который меняет номер в адресе, и злонамеренное вложение в чате.

## 15.1. Вход и сессии

* Пароли хранятся хешем bcrypt (10 раундов); в ответах API хеш не появляется.
* Сессия — JWT в cookie `fsm_session`: `httpOnly`, `SameSite=lax`, `Secure` в production
  (отключается только явным `COOKIE_SECURE=false` для установки без TLS), срок 14 дней.
  Мобильный клиент может присылать тот же токен заголовком `Authorization: Bearer`.
* **Ключ подписи обязателен.** В production при отсутствии `AUTH_SECRET` (или короче 32
  символов) выдача и проверка сессий отключены с явной ошибкой. Раньше подставлялся
  ключ по умолчанию из исходников — зная его, любой мог подписать себе токен
  администратора. Тихо работать с известным ключом опаснее, чем не работать.
* **Подбор пароля ограничен** (`src/lib/login-guard.ts`): 8 неудач по паре «email + адрес»
  за 15 минут — блокировка на 15 минут. Счётчик в памяти процесса: для установки в один
  контейнер этого достаточно, внешнего хранилища не требуется.
* **Смена пароля обрывает прежние сессии.** У пользователя есть отметка
  `password_changed_at`; токен, выданный до неё, не принимается. Себе при смене пароля
  сразу выдаётся новый токен, чтобы человек не оказался выброшен из системы. Раньше
  украденный токен оставался рабочим и после смены пароля.
* Отключение сотрудника или его роли лишает доступа немедленно: состав прав читается из
  базы на каждый запрос, а не берётся из токена.

## 15.2. Права и область видимости

Проверка прав идёт в `withAuth(handler, [права])`; страницы дополнительно закрыты
`requireUser([права])`. Кроме списка прав у роли есть **область видимости**: все данные,
только своя бригада, только свой клиент. Область применяется в запросах (`getTicket`,
`serviceHistory`), а не в интерфейсе.

Исправлено при разборе:

* **Оборудование чужого объекта.** `GET /api/v1/sites/{id}/equipment` проверял право, но
  не проверял, чей это объект: пользователь портала перебором номеров мог получить состав
  оборудования на объектах других клиентов. Теперь объект сверяется с клиентом
  пользователя.
* **Справочники всем подряд.** `GET /api/v1/directories/{dict}` был открыт любому
  авторизованному, включая список ролей вместе с матрицей прав. Теперь пользователю
  портала справочники недоступны вовсе, а роли отдаются только тем, кто управляет ролями
  или сотрудниками.
* **Журнал действий** закрыт отдельным правом `audit.view` — он показывает работу всей
  организации.

## 15.3. Запросы и данные

* Все тела и параметры проходят zod-схемы (`src/lib/validators.ts`); идентификаторы из
  адреса — через `parseId`. Незнакомые поля отбрасываются.
* Запросы к БД параметризованы (Drizzle); имена таблиц в служебных запросах подставляются
  только через `sql.identifier` из внутреннего перечня, не из ввода пользователя.
* **Cross-origin запросы отклоняются.** Для изменяющих методов сверяется заголовок
  `Origin` с адресом системы. `SameSite=lax` уже не даёт чужому сайту отправить cookie,
  но проверка — второй рубеж на случай прокси, переписывающего правила cookie. Запросы
  без `Origin` (мобильный клиент с токеном, curl) не отклоняются: у них нет неявной
  аутентификации через cookie.
* **Тексты внутренних ошибок наружу не уходят.** В production ответ 500 содержит
  нейтральную фразу; подробность драйвера БД (имена таблиц и колонок) остаётся в
  серверном логе.
* Ошибки прав (403) и неудачные входы попадают в журнал действий — см. `docs/14-audit-log.md`.

## 15.4. Вложения

Файлы чата лежат **вне** `public/`, в `UPLOAD_DIR`, под случайным именем без расширения, и
отдаются только через `/api/v1/files/{id}` с проверкой доступа к заявке. Тип определяется
по сигнатуре содержимого, а не по заголовку клиента; inline показываются только растровые
изображения, видео, аудио и PDF, остальное — принудительным скачиванием. Ответ идёт с
`nosniff` и `Content-Security-Policy: sandbox`, поэтому даже открытый в браузере файл не
исполняется в контексте приложения. Ограничения: 50 МБ на файл (`MAX_UPLOAD_MB`), 10
файлов на сообщение.

## 15.5. Заголовки

Общие заголовки задаются в `next.config.ts`:

* `Content-Security-Policy` — источники ограничены собственным адресом: сторонние скрипты,
  кадры и отправка данных наружу запрещены, `object-src 'none'`, `base-uri 'self'`,
  `form-action 'self'`. `script-src` допускает `'unsafe-inline'`: Next вставляет в
  страницы собственные inline-скрипты гидратации.
* `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (микрофон
  запрещён, камера и геопозиция — только своему коду).
* Заголовок `X-Powered-By` отключён.

## 15.6. Демо-данные

На пустой базе создаются демо-роли и сотрудники с паролем из `SEED_PASSWORD`. На странице
входа показываются кнопки демо-доступов: нажатие подставляет логин и пароль нужной роли.
Пока система в разработке, это экономит время на каждом запуске, поэтому блок включён по
умолчанию.

**Перед боевым запуском его нужно выключить** — `SHOW_DEMO_LOGINS=false`: на рабочей
установке это готовая подсказка для входа. Пункт есть и в списке шагов развёртывания ниже.

## 15.7. Что стоит сделать при развёртывании

1. Задать длинный случайный `AUTH_SECRET` (`openssl rand -hex 32`) и свой `SEED_PASSWORD`.
2. Поставить систему за HTTPS-прокси и оставить `COOKIE_SECURE=true`.
3. Выключить демо-доступы на странице входа: `SHOW_DEMO_LOGINS=false`.
4. Сменить пароли демо-учёток или удалить их, оставив своих сотрудников.
5. Раздать право `audit.view` только тем, кому положено читать журнал.
6. Настроить резервное копирование (раздел «Администрирование») и проверить восстановление.

## 15.8. Известные ограничения

* Счётчик неудачных входов живёт в памяти процесса: при нескольких экземплярах приложения
  лимит считается отдельно у каждого. Для одной установки это приемлемо, для кластера
  понадобится общее хранилище.
* Ограничения частоты стоят только на входе; остальные эндпоинты рассчитаны на внутреннюю
  сеть с известными пользователями.
* Двухфакторной аутентификации нет.
* Журнал действий пишет изменения; чтение данных (кто какой отчёт открывал) не пишется.
