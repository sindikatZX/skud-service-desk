# 1. Обзор архитектуры

## 1.1. Назначение системы

**СКУД•Сервис** — self-hosted система класса Service Desk / Field Service Management для компании, выполняющей монтаж, ТО и ремонт систем контроля доступа (СКУД) и видеонаблюдения. Единое рабочее пространство для диспетчеров, монтажных бригад, склада, руководства и клиентов.

## 1.2. Стек технологий и обоснование

| Слой | Технология | Обоснование |
|---|---|---|
| Приложение (frontend + backend) | **Next.js 16 (App Router), TypeScript, React 19** | Один репозиторий и один процесс для UI и REST API упрощают self-hosted эксплуатацию (один контейнер). Серверный рендеринг даёт быстрый первый экран на слабых мобильных устройствах монтажников. Route Handlers образуют чистый версионированный REST API `/api/v1/*`, независимый от UI. |
| База данных | **PostgreSQL 16** | Реляционная модель критична для складского учёта: транзакции, FK-целостность, уникальные индексы (серийные номера), агрегатные отчёты. Зрелый инструментарий бэкапов (`pg_dump`). |
| ORM / миграции | **Drizzle ORM + drizzle-kit** | Типобезопасная схема в коде (`src/db/schema.ts` — единственный источник истины), генерация SQL-миграций, лёгкий рантайм без кодогенерации. |
| Аутентификация | **JWT (HS256, `jose`) в HttpOnly cookie** + `bcryptjs` | Тот же токен принимается в заголовке `Authorization: Bearer` — готово для нативных мобильных клиентов. Без внешних Identity-провайдеров. |
| UI | **Tailwind CSS 4** | Адаптивная вёрстка (mobile-first: карточки на телефоне, таблицы на десктопе, нижняя навигация на мобильных). |
| PWA | Web App Manifest + собственный Service Worker | Установка на домашний экран, кэш app-shell, network-first для страниц и API с оффлайн-фолбэком. |
| Деплой | **Docker + docker-compose** (`app` + `postgres` + опц. `backup`) | Полная автономность на сервере компании; одна команда для установки. |

**Принцип «сервисы — единый источник бизнес-логики».** И страницы (server components), и REST-эндпоинты вызывают одни и те же функции из `src/lib/services/*`. Это гарантирует, что мобильное приложение, использующее только API, получит ровно то же поведение (те же переходы статусов, те же проверки остатков), что и веб-интерфейс.

## 1.5. Ключевые архитектурные решения

1. **Складской журнал как источник истины истории.** Таблица `stock_transactions` — append-only журнал всех движений. Текущие состояния (`equipment_units.status`, `stock_balances.quantity`) — производные, обновляются в одной транзакции с записью журнала.
2. **Серийный vs количественный учёт.** Признак `catalog_items.is_serialized` разводит два режима: серийные единицы (`equipment_units`, жизненный цикл поштучно) и остатки (`stock_balances` + `stock_reservations`).
3. **Машина состояний заявки** описана в одном месте (`TRANSITIONS` в `services/tickets.ts`) вместе с правами на переходы.
4. **История вместо перезаписи** для состава бригад (`team_members.left_at`) и закрепления автомобилей (`vehicle_assignments.released_at`).
5. **API-first.** Единый формат ответа `{ ok, data | error }`, версионирование по URL, поддержка Bearer-токена.

### Конкурентный доступ

Операции, изменяющие состояние, выполняются под блокировкой строки внутри транзакции:

* `changeStatus()` (`src/lib/services/tickets.ts`) читает заявку через `SELECT … FOR UPDATE`, поэтому
  проверка допустимости перехода идёт по актуальному статусу — два одновременных перехода не могут
  разойтись с историей;
* `adjustBalance()` (`src/lib/services/inventory.ts`) сначала гарантирует наличие строки остатка
  (`INSERT … ON CONFLICT DO NOTHING`), затем блокирует её `FOR UPDATE` — параллельные выдачи одной
  позиции не уводят остаток в минус;
* `getUnit()` блокирует серийную единицу на время операции.
