# 14. Журнал действий

Журнал отвечает на вопросы «кто это сделал», «когда» и «что было до этого»: кто списал
материалы и сколько, кто перевёл заявку в закрытую, кто удалил сообщение в чате, кто
менял цену позиции. Это не отладочный лог, а рабочий инструмент разбора спорных
ситуаций, поэтому записи написаны словами, а не кодами.

## 14.1. Где ведётся запись

Записи создаёт слой API — обёртка `withAuth` в `src/lib/api.ts`, а не отдельные вызовы в
сервисах. Причина простая: через `withAuth` проходит каждый изменяющий запрос, и ни одно
действие не останется незаписанным из-за того, что кто-то забыл добавить строчку. В
журнал попадают методы `POST`, `PATCH`, `PUT`, `DELETE`; чтение не пишется — иначе журнал
за неделю превратится в шум, в котором ничего не найти.

Что записывается всегда:

* исполнитель (имя и роль на момент действия), время, IP, метод и адрес запроса;
* действие: создание, изменение, удаление, складская операция, вход, выход, отказ в доступе;
* сущность и её номер — по ним запись связывается с объектом;
* фраза для человека и подробности.

Отдельно записываются **вход и выход** (включая неудачные попытки — по ним видно подбор
пароля) и **отказы по правам**: попытка сделать то, на что прав нет, — это тоже событие,
о котором стоит знать.

## 14.2. Как получается текст записи

Заготовку даёт `describe(method, pathname)` в `src/lib/services/audit.ts`: из адреса
запроса выводится сущность и действие («Удалил заявку #42»). Обработчик роута может
уточнить запись через `ctx.audit.set({...})`, если знает больше:

```ts
export const POST = withAuth(async (req, { user, audit }) => {
  const res = await writeOffDocument({ ...b, actorId: user.id });
  audit.set(await operationDigest(res, "Списал"));
  return ok(res, { status: 201 });
}, ["inventory.writeoff"]);
```

`operationDigest` (в `src/lib/services/inventory.ts`) разворачивает результат складской
операции в человеческую фразу с наименованиями, количествами и складами:

> Списал: 2 поз., всего 3 со склада «Центральный склад» — документ СП-000001
> подробности: позиции — «Замок электромагнитный ML-300 (LOCK-ML-300) — 2 шт»,
> «Блок питания 12В 5А (PSU-12V-5A) — 1 шт»

Названия разворачиваются **при записи**, а не при показе: товар потом могут переименовать
или удалить, а журнал должен читаться и через год.

Для изменений карточек есть `changes(before, after, labels)` — он оставляет только
отличающиеся поля в виде «было → стало» и выбрасывает служебные (`updatedAt`,
`priceUpdatedAt`, хеш пароля):

> Изменил товар «Замок электромагнитный ML-300»: производитель AccordTec → AccordTec-2;
> цена пусто → 1350.00

Если обработчик ничего не уточнил, в подробности попадает тело запроса — так видно, что
именно прислал пользователь. Тело читается только у JSON-запросов до 64 КБ: у выгрузок и
вложений оно весит мегабайты, а пользы в журнале не даёт.

## 14.3. Что в журнал не попадает

`sanitize()` вычищает запись перед сохранением:

* поля, в названии которых есть `password`, `token`, `secret`, `confirm`, — заменяются на `···`;
* значения `data:` (вложенные файлы) — на «вложенный файл»;
* строки длиннее 500 символов обрезаются, массивы — до 20 элементов, вложенность — до 4.

Журнал не должен становиться вторым местом хранения секретов и файлов.

Запись журнала никогда не роняет сам запрос: `recordAudit` ловит свои ошибки и пишет их в
серверный лог. Пользователь уже выполнил действие — отказывать ему из-за сбоя журнала
неправильно.

## 14.4. Экран журнала

`/audit` — таблица с отбором по периоду, сотруднику, действию, разделу и поиском по
тексту (фраза, имя, объект, адрес запроса). Постранично, по 100 записей. Раздел виден
только с правом `audit.view`; у роли «Администратор» оно есть по умолчанию, остальным
выдаётся в справочнике ролей.

Подробности каждой записи разворачиваются по требованию — парами «поле — значение», а не
сырым JSON. Из строки журнала можно перейти к самому объекту (заявке, товару, документу).

На карточке товара тот же журнал показан срезом по позиции — блок «История изменений
карточки» (`auditFor("catalog_item", id)`).

## 14.5. Таблица `audit_log`

| Поле | Смысл |
|---|---|
| `at` | когда (индексировано) |
| `actor_id`, `actor_name`, `actor_role` | кто; имя и роль сохраняются копией — сотрудника могут удалить |
| `action` | create / update / delete / operation / login / logout / denied |
| `entity`, `entity_id`, `entity_label` | над чем действие |
| `summary` | фраза для человека |
| `method`, `path`, `status`, `ip` | техническая часть запроса |
| `details` | подробности (jsonb) |

Индексы: по времени, по исполнителю, по паре «сущность + номер».

Журнал только пополняется: экрана удаления записей нет и в API его тоже нет — иначе
следы можно было бы подчистить из самой системы. Очистка возможна только вручную в БД.
