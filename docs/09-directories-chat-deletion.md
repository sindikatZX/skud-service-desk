# 9. Справочники, чат по заявке и удаление записей

Документ описывает три возможности, добавленные поверх базовой системы, и правила, по которым они работают.

## 9.1. Справочники

Раздел **«Справочники»** (`/directories`, право `directories.manage`) ведёт списки, из которых
заполняются формы. Каждый справочник — отдельная страница, добавление записи не привязано к форме,
где значение используется: категорию оборудования заводят в справочнике, а не на экране создания
номенклатуры.

| Справочник | Адрес | Где используется |
|---|---|---|
| Типы работ | `/directories/ticket-types` | Поле «Тип работ» в заявке |
| Приоритеты и SLA | `/directories/priorities` | Приоритет заявки; `sla_hours` подставляет срок |
| Категории оборудования | `/directories/categories` | Группировка номенклатуры и склада |
| Единицы измерения | `/directories/measure-units` | Номенклатура, акты работ |
| Роли и права | `/directories/roles` | Назначение сотрудникам |

Общие правила:

* **Код** (`code`) — латиницей, уникален внутри справочника, используется в интеграциях;
* **Активность** — снятая галочка убирает запись из выпадающих списков, не трогая историю;
* **Порядок сортировки** задаёт положение в списках;
* **Использований** — сколько записей ссылается на элемент; пока счётчик не нулевой, удаление отклоняется;
* **Системные записи** (помечены «системная») переименовываются и отключаются, но не удаляются.

### Приоритеты и SLA

`sla_hours` — срок исполнения по умолчанию. Если при создании заявки поле «Срок» оставлено пустым,
он вычисляется как «сейчас + SLA приоритета». `color_class` — классы Tailwind, которыми приоритет
подсвечивается в списках.

### Роли

Роль — это набор прав плюс область видимости:

* **Права** отмечаются галочками и сгруппированы по разделам (`PERMISSION_GROUPS` в `src/lib/rbac.ts`);
* **Область видимости** (`scope`): все данные / только своей бригады / только своего клиента;
* **Полевой персонал** (`is_field_staff`) — только такие сотрудники добавляются в бригады и попадают
  в отчёт о загрузке монтажников.

Статусы заявок в справочники намеренно не вынесены: на них завязан автомат переходов
(см. [07-business-processes.md](07-business-processes.md)), поэтому их набор задан в коде.

## 9.2. Чат по заявке

На карточке заявки — лента обсуждения между диспетчером, бригадой и складом.

* Сообщения бывают **внутренними** (по умолчанию) и **открытыми** — открытые видит заказчик в портале.
  Открытые помечены в ленте подписью «виден клиенту».
* Право `chat.write` разрешает писать, `chat.internal` — видеть и отправлять внутренние сообщения.
  Заказчик внутренние сообщения не получает, а его собственные сообщения сервер всегда публикует
  как открытые — независимо от того, что прислал клиент.
* Новые сообщения подтягиваются опросом раз в 7 секунд запросом `?afterId=<последний id>`, а также
  сразу при возврате на вкладку. Веб-сокеты намеренно не используются: развёртывание остаётся
  «docker compose up» без дополнительной инфраструктуры.
* Автор может удалить своё сообщение, администратор (`users.manage`) — любое. Имя автора хранится
  в сообщении, поэтому лента остаётся читаемой после удаления сотрудника.
* В завершённой заявке (`closed` / `cancelled`) лента доступна только для чтения.

## 9.3. Удаление записей

Ошибиться при вводе можно, поэтому удалять разрешено — но так, чтобы не разрушить историю.
Логика собрана в `src/lib/services/deletion.ts`.

Перед удалением система считает ссылающиеся документы и при их наличии отвечает `409 CONFLICT`
с перечнем помех и подсказкой. Общая альтернатива — **деактивация**: запись исчезает из списков,
а история сохраняется.

| Запись | Когда удаление блокируется |
|---|---|
| Клиент | есть заявки, объекты, складские операции или учётные записи портала |
| Объект | есть заявки, установленное оборудование или числящееся на объекте оборудование |
| Сотрудник | есть складские операции или созданные им резервы; нельзя удалить себя и последнего администратора |
| Бригада | есть заявки, оборудование на руках, ненулевые остатки, активные резервы или складские операции |
| Автомобиль | закреплён за бригадой |
| Номенклатура | есть серийные единицы, проводки, установки, резервы или ненулевые остатки |
| Серийная единица | установлена на объекте, зарезервирована или числится в актах установки |
| Заявка | есть установленное оборудование, активные резервы или складские проводки |
| Запись справочника | системная или используется (счётчик «Использований» > 0) |

Особые случаи:

* **Серийная единица** удаляется вместе со своими складскими проводками — это исправление ошибки
  приёмки, а не переписывание истории обслуживания, поэтому установленную единицу удалить нельзя.
* **Заявка** удаляется вместе с историей статусов, работами и чатом; вывод сотрудника из бригады —
  это не удаление, а проставление `left_at`, состав бригады остаётся в истории.
