# 4. Ролевая модель и права доступа

Роли **хранятся в БД** (таблица `roles`) и редактируются в разделе «Справочники → Роли и права»:
администратор может завести собственную роль, отметив галочками нужные права. Набор самих прав
(`Permission`) фиксирован в коде — на него опираются проверки.

Реализация:

* `src/lib/rbac.ts` — перечень прав, их группировка для экрана роли (`PERMISSION_GROUPS`) и описания системных ролей (`SYSTEM_ROLES`);
* `src/lib/auth.ts` — при входе права роли загружаются в сессию (`SessionUser.permissions`);
* проверка в API — `withAuth(handler, [perms])`, на страницах — `requireUser([perms])`;
* область видимости данных задаётся полем роли `scope`, а не кодом роли:

| `scope` | Что видит пользователь |
|---|---|
| `all` | все заявки, клиентов и остатки |
| `team` | только заявки и остатки своей текущей бригады (`team_members.left_at IS NULL`) |
| `client` | только заявки и объекты своего клиента (портал заказчика) |

Признак роли `is_field_staff` отмечает полевой персонал: только таких сотрудников можно включать
в бригаду и по ним строится отчёт о загрузке монтажников.

Системные роли (`is_system = true`) — `admin`, `dispatcher`, `technician`, `warehouse`, `client` —
переименовываются и перенастраиваются, но не удаляются: на их коды опирается первичная настройка
системы. Роль нельзя удалить, пока она назначена хотя бы одному сотруднику; последнюю роль с правом
`users.manage` система также защищает от потери этого права — иначе доступ к администрированию был бы утрачен.

## 4.1. Роли, создаваемые при первом запуске

| Роль | Кто это | Обоснование |
|---|---|---|
| **admin** — Администратор | Руководитель / ИТ | Полный доступ, управление пользователями, бригадами, автопарком, справочниками. Может выполнять любые операции для разбора инцидентов. |
| **dispatcher** — Диспетчер | Менеджер заявок | Принимает заявки, ведёт клиентов и объекты, назначает бригады, планирует выезды, закрывает заявки после подтверждения клиента, резервирует оборудование под заявки, смотрит отчёты по заявкам и сотрудникам. Не выполняет складских отгрузок. |
| **technician** — Монтажник | Член бригады | Видит только заявки своей бригады и остатки своей бригады. Переводит заявки в работу, фиксирует выполненные работы, устанавливает оборудование из остатков бригады (списание на объект), резервирует из остатков бригады, отмечает выполнение (`done`). |
| **warehouse** — Склад | Кладовщик | Приход, отгрузка бригадам, возврат, списание, ведение номенклатуры. Видит все остатки и расход в разрезе бригада/клиент/заявка. Заявки — только на чтение (для понимания, куда ушло оборудование). |
| **client** — Клиент | Контакт заказчика | Создаёт заявки на свои объекты, видит только свои заявки, объекты и установленное на них оборудование. |

Технический принцип: монтажники работают **бригадами**, поэтому область видимости монтажника определяется его *текущей* бригадой (`team_members.left_at IS NULL`), а не персональным назначением. Индивидуальная статистика ведётся через `ticket_works.performed_by`.

## 4.3. Права на переходы статусов заявки

| Переход в статус | Кто может |
|---|---|
| `assigned`, `scheduled`, `new` (возврат) | admin, dispatcher |
| `in_progress`, `on_hold` | technician (своя бригада), admin, dispatcher |
| `done` | technician (своя бригада), admin, dispatcher |
| `closed` | admin, dispatcher |
| `cancelled` | admin, dispatcher |

## 4.4. Область видимости (row-level)

- **technician**: `tickets.team_id = моя бригада`; остатки — только `team_id = моя бригада`; операции резерва/установки — только по заявкам своей бригады и только из её остатков (не со склада).
- **client**: `tickets.client_id = мой клиент`; клиент/объекты — только свои.
- Остальные роли — без ограничений строк (при наличии права).

## 4.5. Аутентификация

- Вход: `POST /api/v1/auth/login` → JWT (14 дней) в HttpOnly-cookie `fsm_session` **и** в теле ответа (`token`) для мобильных клиентов.
- Каждый запрос: cookie **или** `Authorization: Bearer <token>`.
- Заблокированный пользователь (`is_active=false`) теряет доступ немедленно (проверка при каждом запросе).

## 4.4. Права, добавленные вместе со справочниками и чатом

| Право | Что даёт |
|---|---|
| `directories.manage` | Ведение справочников: типы работ, приоритеты и SLA, категории оборудования, единицы измерения, роли |
| `tickets.delete` | Удаление ошибочно созданной заявки (только пока по ней нет складских движений) |
| `chat.write` | Отправка сообщений в чат заявки |
| `chat.internal` | Доступ к внутренним сообщениям чата, скрытым от заказчика |

Заказчик (`scope = client`) внутренние сообщения не видит и отправить их не может: сервер принудительно
публикует его сообщения как открытые.
